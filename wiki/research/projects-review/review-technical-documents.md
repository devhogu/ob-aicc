# Review B: Technical Pilot Blueprint, Journey Technical Profiles, Platform Capability and Readiness Map

Scope: en-6-technical-blueprint, en-7-journey-profiles, en-8-platform-map, checked against the business case, the charter guide, the AI Policy, the Solution Lifecycle Model (5–8), the Operating Model and the Standards Record (ARC, PLT, LAB). No files were edited.

## Verdict

1. The core design is sound and bank-safe in intent: facts come only from systems of record, the model never sets status, the employee approves every action, there is a manual fallback, there is no multi-agent design, and a context-only comparison arm isolates what GenAI actually adds.
2. The three documents are not yet usable as an approval basis. They never mention the AICC path (Risk Tier, Solution Definition, AI Registry, validation by the Control Function Contacts, release by the Domain Owner, the Lab), so the reader cannot tell which decision allows live use.
3. Two design points could push the pilot into Risk Tier 3 or breach data rules: the AI holds write tools, and a managed external model is called "fastest" for customer data with no provider check.
4. The design is over-built for one journey and a small team. It asks for about ten platform components, thirteen IT functions and a three-arm live trial, yet gives no effort, time-box or run cost.
5. About a third of the text repeats itself across the three documents, with small contradictions. The wording is dense, full of jargon and invented capitalized names. Shortening the set and mapping it to the corpus would fix most findings.

## Critical

**C1. No link to the AICC lifecycle; parallel gates replace the corpus approvals.** Blueprint, "Technical validation progression"; Map, "Minimum technical readiness gates" and "CTO decision on reusable platform capabilities". Evidence: "This progression separates permission to mobilize and build from permission to use live customer information"; gates "A — Architecture … Q — Quality → Controlled live readiness". What is wrong: none of the three documents names the Risk Tier, the Solution Definition, the AI Registry entry, validation by the Control Function Contacts (AI Policy 3.3), the Team's final acceptance, the first users, the Domain Owner's release or the Acceptance Checklist (SLM 5.2, 7.1–7.4). The documents invent their own gates and decision makers instead: "CTO", "Sponsor", "controlled live readiness". SLM 7.1 says "no deployment to real users or data comes before" the check or validation. The Map, however, puts "silent evaluation" on live cases under Quality readiness, which reads as coming before the control decision. Recommendation: add one table, in one place, that maps each pilot stage to its corpus state and decision: Definition (Solution Definition approved by the Domain Owner, Risk Tier assigned by the AICC Lead, AI Registry entry made, applicable law confirmed by compliance), Lab experiment on historical extracts, validation (model risk, information security, data protection, conduct), silent read-only run in production, first users, release beyond first users. Express the A/D/C/O/Q gates as evidence for that validation, not as separate approvals. Name the Domain Owner (presumably the Head of Customer Service).

**C2. The AI holds write tools; this risks Risk Tier 3 and contradicts the documents' own limits.** Blueprint, "Registered tools and authority". Evidence: "record_service_outcome | constrained write | record the resulting service state and measurement event"; "create_specialist_referral | constrained write with employee approval"; and, later in the same section, "The pilot does not expose tools that … change an authoritative journey state". What is wrong: AI Policy 3.1 places "an AI agent with rights over systems or funds" in Risk Tier 3, and the documents call the component an "agentic" assistant with a "tool broker". Two writes run without employee approval, and "record the resulting service state" can be read as changing case state. The Journey Profiles add tools that are not in the catalogue ("draft evidence request", "create employee-approved routing/referral"). No document states the expected Risk Tier. Recommendation: give the model read-only functions. All writes (referral, note, outcome record) should be ordinary workspace actions triggered by the employee's click and executed by deterministic code. Write to bank systems only through existing APIs. Write feedback and outcome only to the pilot's own store. State the expected tier as Risk Tier 2 (customer data, output informs work and reaches the customer under human review), and list what would raise it to 3. Use one tool catalogue and have the profiles only remove tools from it.

**C3. Model route and data class: the external managed model is presented as the default, with no provider check.** Blueprint, "Deployment and infrastructure position"; Map, "Model-serving route". Evidence: "Approved managed model through the bank gateway | … fastest validation while retaining provider portability"; "approved managed route or existing internal endpoint through a pilot gateway". What is wrong: the pilot sends contact notes, complaints and payment, dispute or KYC data to the model. AI Policy 2.2, 2.6 and 4.1 require the model to be approved for that data class and the provider to be checked first by information security, data protection and legal (where data is processed and stored, training use, contract terms, fallback and exit). NBKR outsourcing rules and the Law on Personal Information (EXT-001, EXT-002) govern cross-border processing. The historical work belongs in the AICC Lab, which runs on the Bank's own infrastructure and isolated from production (LAB-001, LAB-003, LAB-004, LAB-005), so an external endpoint there is itself a provider decision. "Approved residency" appears only once, as a passing phrase. Recommendation: replace "fastest" with a neutral list of options. State that each route needs approval for the data class and a provider check under AI Policy 4.1 (4.4 for a self-hosted or open model) before any bank data reaches it. Say that the historical evaluation runs in the Lab with a model route approved for that data. Make the data-class decision the first item in the Map's "Decisions required".

## Major

**M1. Too much is built for one journey and a small team.** Blueprint, "Minimum Reusable AI and Controlled-Workflow Foundation", "AI Policy and Security Enforcement", "IT contribution and dependency map"; Map, "Capability map". Evidence: ten "minimum" foundation components (gateway, model and prompt registry, retrieval, evaluation service, AI safety controls, workflow runtime, tool broker, observability, use-case registry, suspension controls), a policy decision service with nine decision points, "event streams or CDC", "an MCP adapter", and thirteen contributing IT functions. What is wrong: AICC runs in light mode with up to three people (SLM 6.6). A mid-size bank cannot staff a "durable, observable state machine" plus a broker, policy service and event spine to serve about 100 live cases. The "minimum" label does not fit. Recommendation: define a minimum build: one service (context assembly, fixed workflow, LLM call, output checks), a side panel in the existing desktop, the AI Platform's gateway (or one thin authenticated proxy), retrieval over one approved corpus, an evaluation harness kept in the repository, and logs that meet PLT-002. Move the policy service, tool broker, MCP, CDC, event spine and "use-case registry" to "later, if a second journey needs them".

**M2. The three-arm live comparison is not feasible as written.** Blueprint, "How the pilot isolates GenAI benefit". Evidence: "The pilot should compare three operating modes … then uses controlled live populations where operationally feasible." What is wrong: the charter guide already estimates 1,000–3,000 eligible cases for each population. Three live arms in one service team multiply that requirement and mix employees across modes. Separately, "the GenAI-assisted mode provides measurable incremental value over the context-only mode" appears as a technical pass criterion, yet the decision diagram treats "Context creates value" as a valid result that leads to investment. Recommendation: compare context-only and GenAI on historical and silent cases, where volume costs little. Run live as existing process against GenAI-assisted, or as a stepped rollout. Make the incremental GenAI value a decision input, not a pass or fail criterion.

**M3. Automatic behaviour that bypasses the change and release rules.** Blueprint, "Operational and SRE expectations" and the CI/CD diagram. Evidence: "progressive release, rollback, model-route failover"; the diagram step "within limits → Expand controlled rollout". What is wrong: a change of model or provider is a significant change (SLM 8.6). The AICC Lead decides whether a new validation is needed, and the Domain Owner releases. An automatic switch to another model route, or an automatic widening of the cohort, skips both. Release beyond the first users needs the Acceptance Checklist (SLM 7.4). Recommendation: allow fallback only to the manual or context-only mode, or to a second model that is already validated. Show cohort expansion as a Domain Owner decision. Route every prompt, model or corpus change through the significance decision of SLM 8.6.

**M4. The scope of the validation progression exceeds the pilot.** Blueprint, "Technical validation progression". Evidence: "Authenticated read-only customer self-service …"; "Limited-authority customer actions only after separate tool, policy, authentication, and customer-confirmation approval." What is wrong: the business case excludes a "customer chatbot" and "autonomous customer action". Customer-facing AI and action tools change the Risk Tier and form a new Solution. Listing them as later steps of this pilot blurs the scope that is being approved. Recommendation: end the progression at "employee-approved communication through an existing channel". Move self-service to "possible future Solutions".

**M5. Content is duplicated across the three documents, with drift.** Evidence: platform and reuse content appears in seven places (Blueprint "Enterprise placement", "Pilot-to-platform evolution", "What is adopted", "What the future platform covers", "Reusable outcome", "CTO scale decision"; Map "CTO decision"; Profiles "Cross-journey reuse"). Capability inventories appear four times (layer view, foundation table, IT contribution map, Map capability map). Decision lists appear twice (Profiles "Profile completion rule" and Map "Decisions required"). Validation lists appear five times. Drift examples: the promotion rule reads "another committed consumer" (Blueprint text), "Second and third consumers committed?" (Blueprint diagram) and "a real second consumer" (Map); the corpus rule is a second consumer (SLM 8.12). Recommendation: each topic lives in one document and the others link to it (see the target structure). Use the corpus's second-consumer rule.

**M6. Terms clash with the corpus.** Evidence: "Technical validation criteria", "Validate facts, citations" (the corpus reserves "Validation" for the Control Function review); "Use-case registry | purpose, owners, sources, model, knowledge, tools, risk tier and approvals" (this duplicates the AI Registry, which the AI Platform feeds under PLT-001); "tool broker", "AI safety controls", "governed retrieval" (the corpus AI Platform has a "tool gateway", "guardrails" and a "knowledge layer"); "assistant", "agent", "agentic workflow" and "AI-assisted workflow" are used interchangeably; the roles named are "CTO", "Sponsor", "Business Sponsor", "Service Owner" and "Agentic Platform Team", with no Domain Owner, AICC Lead, Platform Owner or Control Function Contact; "Controlled evaluation environment" is used where the corpus has the Lab. Recommendation: use "testing" or "evaluation" for technical checks. Feed the AI Registry instead of building a registry. Adopt the AI Platform vocabulary. Use "AI agent" only where the corpus definition applies (actions through tools). Add the corpus roles next to the project roles.

**M7. Approvers lack the facts they need to decide.** All three documents. What is wrong: there is no effort, team size, duration, time-box (required for an Experiment) or run cost and sunset (required for a Service) (SLM 5.2). The documents also omit several Tier 2 obligations: a disclosure decision for AI-drafted customer explanations (AI Policy 2.4, 3.3); bias and error testing before first real use (the Blueprint's test table has none, and LAB-006 requires it); monitoring alert levels with named watchers for performance, drift, override and correction rate, incidents and cost (ARC-008); licenses of open components, models and frameworks (ARC-006, AI Policy 4.4); knowledge-source owner and review date recorded in the AI Registry (ARC-001); and reporting AI Incidents through the Bank's incident management with the AICC Lead notified (AI Policy 5.2–5.4). Recommendation: open the Blueprint with a one-page summary (what is built, what the AI may and may not do, expected Risk Tier, model-route options, what is asked of IT, effort and duration, run cost). Add a short controls table that maps each obligation to the component that meets it.

**M8. Assumptions about bank systems are presented as givens.** Blueprint, "Integration principles", "Service Resolution Workspace", "Data and evaluation assets". Evidence: "Use event streams or CDC"; "Source evidence — deep links to the underlying records"; "consistently tokenized across source systems"; "provide controlled read interfaces, sandbox behavior". What is wrong: many core, card and contact-centre systems at banks of this size lack read APIs, sandboxes, deep links or a shared customer key. Pseudonymizing free-text notes and transcripts consistently across systems is hard and rarely complete. The Profiles handle missing capabilities well; the Blueprint does not. Recommendation: list these as discovery questions with a fallback (a scheduled extract, the record ID shown instead of a link, Lab-only use of identifiable data under LAB-004). Remove "CDC" from the pilot.

**M9. The Blueprint commits to a journey before selection.** Blueprint, "Technical proposition". Evidence: "The recommended first implementation is a Payment Issue Resolution Workspace". What is wrong: the charter guide says the Sponsor selects by the selection rule, and the business case says the problem and ownership "are agreed before detailed solution architecture, platform selection". Recommendation: call Payment a technical recommendation subject to selection, and keep the Blueprint journey-neutral.

## Minor

**m1. Invented capitalized names.** Examples: "Purpose-bound Customer Context Service", "Limited-Authority Service Resolution Assistant", "Minimum Reusable AI and Controlled-Workflow Foundation", "Payment Issue Resolution Workspace", "Banking Tool Broker", "Controlled AI Gateway", "Customer Intelligence and Action Platform", "Enterprise AI and Agentic Workflow Platform". Recommendation: use plain lower-case descriptions ("customer context service", "service resolution assistant", "AI gateway") and the corpus "AI Platform". Write "customer intelligence" in lower case unless it is a defined term.

**m2. Undefined jargon and acronyms.** Examples: "CIAP", "L1 inference service", "L1/L2 model service", "VRAM", "CDC", "A2A", "MCP", "façade", "idempotency and compensation", "reranking", "quantization", "event spine", "SLOs", "DevSecOps", "sidecar". Recommendation: define each one once in a short glossary, or replace it ("a separately run in-bank model service" instead of "L1 inference service").

**m3. Long list-sentences.** Example: "It receives a dedicated workload identity, data purpose, deployment boundary, source allow-list, knowledge corpus, tool allow-list, evaluation set, telemetry stream, and suspension control." The Map's purpose sentence and the hardware paragraph are similar. Recommendation: turn them into short bullets or split them into two sentences.

**m4. Vague or promotional claims.** Examples: "This avoids two opposite risks", "The pilot produces more than a single assistant", "This end-to-end pilot gives IT a concrete solution to estimate and challenge" (but no estimate is given), "immutable or protected decision and action evidence with privacy-aware content logging". Recommendation: state the concrete requirement or cut the sentence.

**m5. Hardware sizing is out of place.** Blueprint, "Deployment and infrastructure position". Evidence: "hardware cannot be responsibly selected from the word 'agent'". The point is correct (orchestration needs no GPU), but the paragraph on sizing and interconnect belongs in a later on-prem decision. Recommendation: keep two sentences and move the rest to the Map's model-route decision.

**m6. The validation progression is out of order.** Blueprint. Evidence: step 1 "Historical case reconstruction and blinded SME evaluation" comes before the context service and the GenAI interpretation that it evaluates, and "Evidence validation, policy tests, and regression gates" comes after them. Recommendation: separate SME labelling of the locked cases (first) from evaluation of the system (after it is built). Build the tests alongside each component.

**m7. Data minimization in the information table.** Blueprint, "Banking systems and information required". Evidence: "customer identity, servicing relationship, segment and relevant preferences". Recommendation: drop "segment" unless the journey needs it (AI Policy 2.5), or justify it in the context contract.

**m8. Headings.** Examples: "Executive visual — from banking facts to reusable platform" and "Technical proposition". Recommendation: use plain headings ("Overview", "What the pilot builds").

**m9. Strengths to keep.** The Profiles' "If the capability is unavailable or unreliable" column, the KYC "no data path" boundary with architecture tests, "GenAI must not compensate for a missing source of truth", locked acceptance cases owned by non-builders (consistent with SLM 7.5), and the position that the gateway lets the bank choose a model later. Keep all of these.

## Proposed target structure

**Technical Blueprint: keep, rename to "Technical design", and cut to about 40% of its length.** 1) One-page summary for approvers (what is built, what the AI may and may not do, expected Risk Tier, model-route options pending the provider check, asks of IT, effort, duration, run cost). 2) Architecture: one diagram and five plainly named components. 3) Information paths: historical extracts in the Lab, and the live read path. 4) What the AI does and which tools it has: one catalogue, read-only for the model, writes by employee action. 5) Controls: a table mapping each obligation (AI Policy Tier 2, ARC-001 to ARC-008, PLT-001/002/004/005) to the component that meets it. 6) Testing and evaluation: test layers plus the GenAI-against-context comparison. 7) Link to the single stages-and-approvals table in the Map. Cut "Capability-layer view", "Minimum Reusable … Foundation", "IT contribution and dependency map" and the platform-evolution sections; merge them into the Map. Reduce the hardware text to two sentences. Remove customer self-service from scope.

**Journey Technical Profiles: keep.** This is the clearest of the three. Changes: add the data classes and the Risk Tier attributes for each journey. Align the tool lists with the single catalogue (removals only). Move the "Profile completion rule" into the Map's decision record and link to it. Shorten "Cross-journey reuse" to a short paragraph.

**Platform Capability and Readiness Map: keep, rename to "IT capability and readiness checklist", and make it the single home for decisions and gates.** 1) Dispositions (reuse, extend, pilot-local, narrow). 2) One capability table that merges the Blueprint's layer view, foundation table and IT contribution map, with columns for capability, pilot need, minimum pilot option, owner and later. 3) One decision record that merges "Decisions required" with the profile completion rule and puts the data-class and provider decision first. 4) One stages-and-approvals table mapped to the corpus states and decision makers, with the A/D/C/O/Q gates as validation evidence. 5) After the pilot: promotion to the AI Platform under the second-consumer rule (SLM 8.12), decided with the Platform Owner, replacing both "CTO decision" sections.
