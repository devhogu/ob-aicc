Это руководство для тех, кто уже пользуется Claude Code для отдельных задач и хочет перейти к долгой работе с меньшим присмотром: поставить цель, уйти — и вернуться к проверяемому результату. Оно пересказывает курс Claude Code in Action и сверено с официальной документацией на русском; там, где курс расходится с документацией, верна документация.

После него вы сможете ставить Claude Code проверяемую цель и оставлять его работать, выбирать режим разрешений и способ автоматизации под задачу, проверять результат по diff, а не по резюме, — и знать, какие настройки важны для регулируемой организации.

Главная мысль курса: чем меньше вы смотрели, тем больше проверяете. Автономия без проверки — это не экономия, а отложенный риск.

Основы, на которые оно опирается, — в Как работает Claude Code и Приёмы, которые работают.

1. Управление долгим сеансом

Две привычки: сначала задать рамки, потом направлять. План из режима планирования нужно действительно прочитать, а не пролистать: поправить план быстрее, чем потом разбирать результат.

Направленное сжатие

/compact Сосредоточься на реализации флага --version — текст после команды решает, что останется в сжатой истории. Это «руль» для контекста.

Откат с вариантами

Двойной Esc на пустой строке открывает точки возврата — каждая ваша реплика создаёт такую точку. Варианты:

Вариант Когда
Вернуть код и разговор Claude ушёл не туда — начать с точки заново
Вернуть только разговор / только код разойтись частично
Сжать начиная отсюда убрать побочную ветку разговора, сохранив начало
Сжать до этого места свернуть долгую подготовку, оставив реализацию целиком

Откат не возвращает то, что сделано командами оболочки (например, установленные пакеты), и правки фоновых помощников — на это есть только git.

Цель: работать до результата

/goal все тесты в src/billing проходят, проверка типов — ноль ошибок — Claude продолжает работу, пока условие не выполнено. После каждого шага отдельная быстрая модель читает разговор и решает: выполнено, не выполнено или невозможно. /goal clear — снять цель, /goal без слов — состояние.

Хорошее условие — проверяемое по выводу самого Claude:

/goal npm test завершается с кодом 0, ни один существующий тестовый файл не изменён, или остановись после 20 ходов
  • Одно измеримое конечное состояние, способ доказательства, запреты и предел ходов.
  • Цель не меняет режим разрешений: для работы без присмотра её сочетают с режимом Auto.
  • Цель снимается сама при ошибке, которую должен исправить человек: вход, лимит, переполнение.
  • Правило курса: ставьте цель, когда «готово» описать проще, чем шаги.
  • Для чувствительного репозитория работа без присмотра может быть неприемлема. Тогда ставьте цель в ручном режиме: Claude будет останавливаться на каждом вопросе, а вы — подтверждать.

Попробуйте: в отдельной ветке поставьте /goal с условием «npm test (или ваша команда тестов) завершается с кодом 0, ни один существующий тестовый файл не изменён, или остановись после 20 ходов». Когда Claude закончит, сначала прочитайте git diff и только потом — его резюме.

Опрос по расписанию в сеансе

/loop 5m проверь, закончилось ли развёртывание — повторять запрос с интервалом; без интервала Claude сам выбирает паузу от минуты до часа. Работает, пока открыт сеанс; повторы истекают через семь дней.

Параллельные сеансы

claude --worktree имя (или -w) — отдельная копия репозитория на своей ветке, чтобы два сеанса не мешали друг другу. Файл .worktreeinclude перечисляет неотслеживаемые файлы (настройки окружения), которые копировать в каждую копию. Каталог .claude/worktrees/ добавьте в .gitignore.

Дальше: CLAUDE.md, который соблюдается →

2. CLAUDE.md, который соблюдается

CLAUDE.md — рекомендация, а не принуждение: строки соревнуются за внимание, и чем длиннее файл, тем хуже соблюдается каждое правило.

  • Жёсткие правила вроде «никогда не отправлять в main» — не в CLAUDE.md, а в хук (см. «Хуки»).
  • Четыре уровня загружаются вместе: политика организации (её нельзя отключить), ваш личный, проектный (в git) и локальный CLAUDE.local.md (не в git — например, решения вашей ветки).
  • Импорты вида @.claude/conventions/code-style.md помогают организовать файл, но контекст не уменьшают: импортированное подставляется целиком.

Как формулировать

Слабее Сильнее
«Соблюдай структуру проекта» «Новые обработчики API — в src/api/handlers, по одному на файл»
«Не используй default export» «Используй именованные экспорты, а не экспорт по умолчанию»
  • Конкретно и проверяемо; называйте, что делать вместо.
  • Выделение «ВАЖНО» — бюджет на 2–3 действительно важных правила, не больше.
  • Каждая ошибка Claude — отчёт об ошибке в CLAUDE.md: «добавь это в CLAUDE.md». И наоборот: строку, которую не можете обосновать, удаляйте.
  • Совет курса: начните без CLAUDE.md, посмотрите, где приходится поправлять Claude, и только потом /init.

Дальше: Навык проверки →

3. Навык проверки

Первый навык, который стоит написать, — проверка. Он срабатывает после изменений: запустить тесты → прочитать diff → убедиться, что ни один тест не ослаблен → отчёт «прошло/не прошло» с доказательствами.

«Готово» — это не «код выглядит правильно». Готово — это когда проверки запущены и результат назван явно.

---
name: verify-changes
description: Проверяет изменения после правок кода — тесты, diff, ослабленные
  тесты — и даёт отчёт с доказательствами. Используй после любого рефакторинга
  и перед коммитом.
---
1. Запусти ./scripts/check.sh и покажи вывод целиком.
2. Прочитай git diff. Найди тесты, которые пропущены, удалены или ослаблены.
3. Найди новые зависимости и вписанные в код адреса и ключи.
4. Найди реальные данные клиентов в тестах и примерах.
5. Отчёт: прошло / не прошло, по каждому пункту — доказательство.

Положите навык в .claude/skills проекта — и он будет у всей команды. Что куда: CLAUDE.md — постоянные правила; навык — процедура под тип задачи; хук — то, что нельзя пропустить. Правило: дважды набрали одну и ту же многошаговую инструкцию — это навык. Подробно — Навыки Claude: полное руководство.

Дальше: Режимы разрешений →

4. Режимы разрешений

Режим Что делает Где уместен
Manual спрашивает перед правками и командами чувствительный код, начало работы
Accept edits правит файлы и простые файловые команды без вопроса знакомая задача под присмотром
Plan только изучает и предлагает план разобраться до правок
Auto отдельная модель проверяет каждое действие и блокирует опасное работа без присмотра
Don't ask выполняет только заранее разрешённое, остальное молча отклоняет CI, задания по расписанию — ничего не «зависнет» на вопросе
Bypass без каких-либо проверок только в изолированном контейнере без сети
  • Shift+Tab переключает Manual, Accept edits, Plan и Auto.
  • В новых версиях интерактивные сеансы начинаются в режиме Auto.
  • Важно: проверка в Auto оценивает намерение, а не правильность. Сломанная авторизация пройдёт проверку — «сломанное не значит опасное». Поэтому Auto сочетают с хуком, который гоняет тесты.

Дальше: Хуки: то, что должно произойти →

5. Хуки: то, что должно произойти

Около тридцати событий; ключевые для долгой работы:

Событие Зачем
PreToolUse главный инструмент принуждения: запретить, разрешить или изменить действие до выполнения
PostToolUse форматирование и проверки после правки
Stop / SubagentStop «ты ещё не закончил»: не дать завершиться, пока тесты не проходят
SessionStart с фильтром compact вернуть ключевые правила после сжатия контекста
InstructionsLoaded аудит того, что попало в контекст

Коды выхода

  • 2 — заблокировать (сообщение уйдёт Claude). Stop с кодом 2 не даст сеансу завершиться.
  • 1 — не блокирует, только сообщает об ошибке.
  • PostToolUse блокировать поздно: действие уже выполнено.

Где хуки ненадёжны

  • PreToolUse, упавший по таймауту, пропускает действие.
  • Stop-хук снимается после восьми блокировок подряд без действий — проверяйте поле stop_hook_active.
  • Если организация разрешила только управляемые хуки, перестаёт работать /goal.

Полезный приём — «замаскировать, а не запретить»: PreToolUse находит в команде секретный ключ и подменяет его заглушкой, вместо того чтобы останавливать работу. Основы — в руководстве Хуки в Claude Code.

6. Запуски по расписанию и без диалога

Лестница выбора — от «ничего не строить» к собственной программе:

  1. Routinesзапрос + репозиторий + подключения + запуск по расписанию, вызову или событию GitHub; работает в облаке Anthropic
  2. claude -pзапуск из скрипта или CI без диалога
  3. Agent SDKсобственная программа с Claude внутри

Routines

/schedule ежедневная проверка зависимостей в 9:00 или через claude.ai/code/routines. Минимальный интервал — час; запуск из свежей копии основной ветки; отправка изменений — только в ветки claude/*. Все подключения по умолчанию включены — уберите лишние; сеть держите в режиме «Trusted (Доверенная)»; защитите основную ветку так, чтобы подключённый аккаунт не мог обойти защиту. Владелец организации может выключить routines совсем.

claude -p

claude -p "кратко опиши изменения в этом diff"

# структурированный ответ по схеме
claude -p "перечисли функции модуля" --output-format json \
  --json-schema '{...}' | jq '.structured_output'

# без присмотра: только заранее разрешённое
claude -p "исправь ошибки линтера" --permission-mode dontAsk \
  --allowedTools "Edit,Bash(npm run lint *)"

Важное расхождение с курсом. Сам по себе -p загружает тот же контекст, что и обычный сеанс, — включая хуки из .claude/settings.json и подключения из .mcp.json репозитория, причём без диалога доверия. Пропускает их только флаг --bare. Для CI на чужом или непроверенном коде используйте --bare и явно передавайте нужное флагами (--settings, --mcp-config). --bare даёт воспроизводимую настройку, а не одинаковый ответ модели, и требует ключа API. Если ключа API нет, есть флаг --setting-sources user: с ним Claude Code не читает ни настройки проекта, ни его .mcp.json.

Успех запуска — код выхода 0; для --output-format stream-json смотрите и список отклонённых действий.

Дальше: Запросы на слияние: Code Review и GitHub Actions →

7. Запросы на слияние: Code Review и GitHub Actions

Code Review

Управляемый сервис ревью PR: включает администратор; запуск при открытии PR, при каждой отправке изменений или по @claude review. Анализирует изменения на фоне всей кодовой базы, оставляет комментарии с уровнем серьёзности. Никогда не одобряет и не блокирует PR. Исправлять — локально: /code-review --fix. Недоступен в конфигурациях без хранения данных и HIPAA.

GitHub Actions

/install-github-app (нужны права администратора репозитория), действие anthropics/claude-code-action. Запуск по упоминанию @claude или по своему запросу и расписанию. Для отчётов — только инструменты на чтение и без вопросов.

Правила для Actions: секреты — только через GitHub Secrets или федерацию удостоверений; минимальные права для рабочих процессов GitHub Actions; предел ходов --max-turns, таймауты и ограничение параллельных запусков; слияние — только после ревью человеком.

Дальше: Проверка работы без присмотра →

8. Проверка работы без присмотра

  1. Глубина проверки — по степени автономииЧем меньше вы видели, тем строже проверка.
  2. Сначала diff, потом резюмеРезюме пишет тот, кто работал; diff не врёт. Сначала файлы из плана, потом всё, что вне плана.
  3. /code-review и «холодный» помощникСвежий взгляд без памяти о том, как писался код. Уровни: /code-review low, /code-review high.
  4. Тесты как воротаStop-хук с тестами плюс PostToolUse с линтером и проверкой типов; код 2 возвращает ошибку Claude.
  5. Не ослаблены ли тестыПропущенные, удалённые и «смягчённые» тесты — отдельная проверка.
  6. Для запусков из скриптовСмотрите JSON-результат и код выхода, а не только текст.

Три кучки находок

Находки ревью раскладывайте на три кучки: исправить сейчас / спросить почему / оставить. Ревьюер, которого попросили искать проблемы, найдёт их всегда; если гнаться за каждой, код обрастает лишними абстракциями. Принимайте то, что влияет на правильность и требования.

Хорошие запросы:

Проверь изменения, которые ты только что сделал. Сообщи о проблемах, ничего пока не исправляй.

Ты написал, что isValidEmail не обрезает пробелы, но в строке 4 вызывается trim(). Проверь ещё раз: находка в силе?

Исправь первую находку. Затем запусти тесты и покажи вывод.

Дальше: Параллельная работа и плагины →

9. Параллельная работа и плагины

Фоновые сеансы (Agent view)

claude agents — один экран со всеми фоновыми сеансами и их статусами (работает, ждёт ответа, завершён, ошибка). claude --bg --name "flaky-test-fix" "…" — запустить в фоне. Учтите: фоновый сеанс работает в отдельной копии репозитория и может сам делать коммит, отправку и черновой PR (кроме отправки в main, принудительной отправки и слияния). Если git должен оставаться под ручным контролем — пропишите это в CLAUDE.md. Каждый фоновый сеанс расходует лимит отдельно.

Динамические сценарии (workflows)

Для задач на десятки и сотни шагов Claude пишет план-сценарий, который запускает множество помощников: «исправляй, пока npx tsc --noEmit не пройдёт или два круга не дадут прогресса», «проверь каждый изменённый файл и дай одну сводку». Встроенный /deep-research вопрос — исследование. Ход — в /workflows. Перед запуском показывается план; пределы — 16 агентов одновременно; для больших запусков — предупреждение о расходе. Организация может отключить сценарии.

Помощники в параллель

«Исследуй модули авторизации, базы данных и API параллельно, отдельными помощниками»; /batch инструкция делит изменение на 5–30 помощников, каждый в своей копии. Сначала — на 2–3 файлах, потом на всём. Подробно о помощниках — Помощники в Claude Code.

Плагины

Плагин объединяет навыки, помощников, хуки и подключения: /plugin install github@claude-plugins-official; командный каталог — /plugin marketplace add организация/claude-plugins. Плагин выполняет код с вашими правами, а его хуки добавляются к вашим. Версионируйте плагины как зависимости.
