После этого руководства вы сможете взять готовый рецепт — разобраться в чужом коде, исправить ошибку, написать тесты, подготовить PR — и пройти его в своём репозитории.

Каждый рецепт — цепочка запросов: начинайте с широкого вопроса и сужайте. Запросы можно писать по-русски.

<div class="rai-cards rai-cards--3">
<article><h3>Разобраться в чужом коде</h3><p>«Дай обзор этого проекта» → «какие основные архитектурные решения?» → «где ключевые модели данных?» → «как устроена авторизация?». Попросите глоссарий терминов проекта.</p></article>
<article><h3>Найти нужное место</h3><p>«Найди файлы, которые отвечают за вход пользователя» → «как они связаны?» → «проследи вход от интерфейса до базы».</p></article>
<article><h3>Исправить ошибку</h3><p>Дайте команду, которая воспроизводит ошибку, и текст ошибки → попросите несколько вариантов исправления → примените выбранный → проверьте.</p></article>
<article><h3>Переработать код</h3><p>«Найди устаревшие вызовы API» → «предложи, как переписать utils.js» → «перепиши, сохранив поведение» → «запусти тесты». Мелкими шагами.</p></article>
<article><h3>Тесты</h3><p>«Какие функции не покрыты тестами?» → «добавь тесты» → «добавь граничные случаи» → «запусти и исправь падения». Claude повторит стиль ваших тестов. Тестовые данные — только вымышленные.</p></article>
<article><h3>Запрос на слияние (PR)</h3><p>«Кратко опиши мои изменения» → «создай PR» → «дополни описание». Перед отправкой попросите назвать риски. Ревью коллегой это не заменяет.</p></article>
<article><h3>Документация</h3><p>«Найди функции без комментариев» → «добавь документацию» → «улучши примерами» → «проверь по нашему стандарту».</p></article>
<article><h3>Картинки</h3><p>Вставьте скриншот ошибки, макет или схему: «что здесь не так?», «сверстай по этому макету». На скриншоте не должно быть данных клиентов.</p></article>
<article><h3>Не только код</h3><p>Claude Code работает в любой папке — заметки, документация, наборы markdown-файлов: искать, править, переупорядочивать.</p></article>

## Попробуйте сейчас: тесты к одному модулю {#try}

1. «Какие функции в `путь/к/модулю` не покрыты тестами?»
2. «Напиши к ним тесты в стиле существующих. Данные — только вымышленные. Код модуля не меняй».
3. «Запусти тесты и покажи вывод».
4. Сами посмотрите `git diff`: изменены только файлы тестов, в них нет реальных данных, ни одна существующая проверка не ослаблена.

## Полезные приёмы {#tricks}

- `@путь/к/файлу` — включить файл в запрос сразу; `@папка` — показать её структуру.
- `claude --continue` — продолжить вчерашнюю работу; `/rename` — дать сеансу понятное имя.
- `claude --worktree имя` — второй сеанс на отдельной ветке, чтобы правки не мешали друг другу.
- `claude --permission-mode plan` или Shift+Tab — сначала план, потом правки.
- «Поручи помощнику выяснить, как устроено обновление токенов» — помощник (subagent) исследует в своём контексте, и основной разговор не засоряется. Подробно — в [Помощники в Claude Code](page:kb/guides/claude-code-subagents).
- `git log --oneline -20 | claude -p "кратко опиши последние коммиты"` — Claude в скриптах, без диалога. Учтите: такой запуск без флага `--bare` выполняет хуки и подключения MCP, настроенные в репозитории, и не спрашивает, доверяете ли вы папке. В чужом или непроверенном репозитории так не запускайте — подробно в [Claude Code в действии](page:kb/guides/claude-code-in-action#headless).

Запуская Claude из скрипта или по расписанию, формулируйте запрос особенно ясно — что считается успехом и куда девать результат: уточнить у вас Claude не сможет.
