После этого руководства вы сможете довести CLAUDE.md до короткой рабочей памятки, настроить разрешения — что можно без вопросов, а что нельзя никогда, — и выбрать, чем закрыть повторяющуюся работу: навыком, помощником, хуком или подключением.

Несколько минут настройки делают каждый следующий сеанс заметно лучше.

CLAUDE.md — короткая памятка проекта

Claude читает этот файл в начале каждого сеанса. Заготовку создаёт /init; доводите её со временем. Для каждой строки спрашивайте себя: «Если её убрать, Claude начнёт ошибаться?» Если нет — удаляйте.

Включать Не включать
Команды сборки и тестов, которые нельзя угадать То, что видно из кода
Правила стиля, отличные от обычных Общеизвестные правила языка
Как называть ветки и оформлять PR Подробную документацию API (лучше ссылка)
Решения по архитектуре, особенности окружения Часто меняющиеся сведения, длинные объяснения

Пример фрагмента для проекта в регулируемой среде (команды замените своими):

# Сборка и тесты
- Сборка: ./gradlew build
- Тесты одного модуля: ./gradlew :payments:test

# Правила
- Работать только в текущей ветке; коммит и отправку делает разработчик
- Не читать и не править .env и каталог secrets/
- Тестовые данные — только вымышленные, без реальных данных клиентов
- Миграции базы данных не менять без отдельного согласования

Если Claude упорно нарушает правило из файла — скорее всего, файл слишком длинный и правило теряется. Храните CLAUDE.md в git: он становится ценнее со временем. Помните, что CLAUDE.md — просьба, а не гарантия: то, что нельзя никогда, закрывайте разрешениями и хуками.

Разрешения

Режим разрешений задаёт общее поведение (режимы описаны в Как работает Claude Code). Для чувствительного кода выбирайте ручной режим: каждое действие проходит через вас.

Правила разрешений уточняют режим для отдельных команд и файлов: allow — безопасное и частое без вопросов (линтер, тесты), deny — то, что нельзя никогда. Посмотреть и изменить правила можно командой /permissions или в файле настроек: ~/.claude/settings.json — ваши личные, .claude/settings.json — общие для проекта (хранятся в git). Пример по документации:

{
  "permissions": {
    "allow": [
      "Bash(npm run lint)",
      "Bash(npm run test *)"
    ],
    "deny": [
      "Read(./.env)",
      "Read(./.env.*)",
      "Read(./secrets/**)"
    ]
  }
}
  • Запрет на чтение действует на встроенные инструменты Claude и на распознаваемые команды вроде cat, но не на программу, которая открывает файлы сама (например, скрипт на Python). Для защиты на уровне системы включите изолированную среду (песочницу) командой /sandbox.
  • Файл .claudeignore Claude Code не учитывает — переносите его записи в правила deny.
  • Надёжнее всего — не держать настоящих секретов в рабочей копии вовсе.

Что выбрать для повторяющегося

Навык

Знания и процедуры, нужные иногда: .claude/skills/имя/SKILL.md. Claude подключает сам или по команде /имя. Подробно — Навыки в Claude Code.

Помощник

Отдельный исполнитель со своим контекстом и инструментами — например, ревьюер безопасности: .claude/agents/. Подробно — Помощники.

Хук

Команда, которая выполняется каждый раз без исключений: проверка после правки, запрет записи в папку. Подробно — Хуки.

Подключения (MCP)

Доступ к трекеру задач, базе данных, документации — командой claude mcp add, если подключение одобрено. Подробно — Подключения MCP.

Правило выбора: CLAUDE.md — то, что нужно всегда; навык — то, что нужно иногда; хук — то, что должно происходить обязательно.

Безопасность

CLAUDE.md, навыки и настройки проекта лежат в git и читаются в каждом сеансе — паролей, ключей и токенов в них быть не должно. Подключайте только одобренные инструменты и смотрите изменения (git diff) перед коммитом.

Попробуйте: добавьте в .claude/settings.json проекта правило deny для файлов с секретами, откройте новый сеанс и попросите Claude прочитать .env — он должен получить отказ. Проверьте правила командой /permissions.
