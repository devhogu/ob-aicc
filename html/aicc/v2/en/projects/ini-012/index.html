Problem and outcome

ProblemFunctions have small, recurring needs: an assessment, a revision of criteria, a risk tier record, follow-up actions after monitoring. Setting up a separate project for each is too heavy.
Intended outcomePrompt, clear support: for every request, the requester, priority, acceptance criteria, and result are recorded, and the work fits into one iteration.
How we measure itShare of requests taken into an iteration and accepted before it ends; share of accepted requests with the delivered result, the criteria met, and the date recorded.
Where we are nowNo requests in progress yet, so the shares are not calculated.
Where we want to beEvery request we take on fits into the iteration and is accepted against its criteria.

Conditions

AppetiteOne iteration per request, out of the Hub team's shared capacity.
Review pointOnce a week we review the queue and take on the highest-priority request that fits into the iteration.
Exit criterionThe requester has accepted the result against acceptance criteria named in advance.
Stop thresholdThe request does not fit into one iteration.

Practice checklist

  • ○ The person who needs the result and the expected benefit are named not started
  • ○ Acceptance criteria are recorded not started
  • ○ If AI is used: the purpose of use and the data class are named not started
  • ○ There is room within the WIP limit and the request fits into one iteration not started
  • ○ The result has been handed to the requester and accepted against the criteria not started

Now

Next step. Collect the functions' first requests for assessment and review.

Main risks

  • A request does not fit into one iteration: then we set it up as a separate project.
  • The team's shared capacity is limited: an urgent request changes the order but adds no extra hands.

Dependencies

  • Free room within the WIP limit.
  • A representative of the function that needs the result.
  • If AI is used: a review of the purpose of use and the data class.
