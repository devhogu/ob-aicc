После этого руководства вы сможете ставить Claude Code проверяемую цель и оставлять его работать, выбирать режим разрешений и способ автоматизации под задачу, проверять результат по diff, а не по резюме, — и знать, какие настройки важны для регулируемой организации.

Это руководство для тех, кто уже пользуется Claude Code для отдельных задач и хочет перейти к **долгой работе с меньшим присмотром**: поставить цель, уйти — и вернуться к проверяемому результату. Оно пересказывает курс Claude Code in Action и сверено с официальной документацией на русском; там, где курс расходится с документацией, верна документация.

Главная мысль курса: **чем меньше вы смотрели, тем больше проверяете.** Автономия без проверки — это не экономия, а отложенный риск.

Основы, на которые оно опирается, — в [Как работает Claude Code](page:kb/guides/claude-code-how-it-works) и [Приёмы, которые работают](page:kb/guides/claude-code-best-practices).

## Управление долгой сессией {#steer}

Две привычки: **сначала задать рамки, потом направлять**. План из режима планирования нужно действительно прочитать, а не пролистать: поправить план быстрее, чем потом разбирать результат.

### Направленное сжатие {#compact}

<code>/compact Сосредоточься на реализации флага --version</code> — текст после команды решает, что останется в сжатой истории. Это «руль» для контекста.

### Откат с вариантами {#rewind}

Двойной <code>Esc</code> на пустой строке открывает точки возврата — каждая ваша реплика создаёт такую точку. Варианты:

| Вариант | Когда |
| --- | --- |
| Вернуть код и разговор | Claude ушёл не туда — начать с точки заново |
| Вернуть только разговор / только код | разойтись частично |
| Сжать начиная отсюда | убрать побочную ветку разговора, сохранив начало |
| Сжать до этого места | свернуть долгую подготовку, оставив реализацию целиком |

Откат не возвращает то, что сделано командами оболочки (например, установленные пакеты), и правки фоновых помощников — **на это есть только git**.

### Цель: работать до результата {#goal}

<code>/goal все тесты в src/billing проходят, проверка типов — ноль ошибок</code> — Claude продолжает работу, пока условие не выполнено. После каждого шага отдельная быстрая модель читает разговор и решает: выполнено, не выполнено или невозможно. <code>/goal clear</code> — снять цель, <code>/goal</code> без слов — состояние.

Хорошее условие — **проверяемое по выводу самого Claude**:

```
/goal npm test завершается с кодом 0, ни один существующий тестовый файл
не изменён, или остановись после 20 ходов
```

- Одно измеримое конечное состояние, способ доказательства, запреты и предел ходов.
- Цель не меняет режим разрешений: для работы без присмотра её сочетают с режимом Auto.
- Цель снимается сама при ошибке, которую должен исправить человек: вход, лимит, переполнение.
- Правило курса: **ставьте цель, когда «готово» описать проще, чем шаги.**
- Для чувствительного репозитория работа без присмотра может быть неприемлема. Тогда ставьте цель в ручном режиме: Claude будет останавливаться на каждом вопросе, а вы — подтверждать.

**Попробуйте:** в отдельной ветке поставьте `/goal` с условием «`npm test` (или ваша команда тестов) завершается с кодом 0, ни один существующий тестовый файл не изменён, или остановись после 20 ходов». Когда Claude закончит, сначала прочитайте `git diff` и только потом — его резюме.

### Опрос по расписанию в сессии {#loop}

<code>/loop 5m проверь, закончилось ли развёртывание</code> — повторять запрос с интервалом; без интервала Claude сам выбирает паузу от минуты до часа. Работает, пока открыта сессия; повторы истекают через семь дней.

### Параллельные сессии {#worktrees}

<code>claude --worktree имя</code> (или <code>-w</code>) — отдельная копия репозитория на своей ветке, чтобы две сессии не мешали друг другу. Файл <code>.worktreeinclude</code> перечисляет неотслеживаемые файлы (настройки окружения), которые копировать в каждую копию. Каталог <code>.claude/worktrees/</code> добавьте в <code>.gitignore</code>.

## CLAUDE.md, который соблюдается {#claude-md}

CLAUDE.md — **рекомендация, а не принуждение**: строки соревнуются за внимание, и чем длиннее файл, тем хуже соблюдается каждое правило.

- **Жёсткие правила** вроде «никогда не отправлять в main» — не в CLAUDE.md, а в хук (см. «Хуки»).
- Четыре уровня загружаются вместе: политика организации (её нельзя отключить), ваш личный, проектный (в git) и локальный <code>CLAUDE.local.md</code> (не в git — например, решения вашей ветки).
- Импорты вида <code>@.claude/conventions/code-style.md</code> помогают организовать файл, но **контекст не уменьшают**: импортированное подставляется целиком.

### Как формулировать {#rules}

| Слабее | Сильнее |
| --- | --- |
| «Соблюдай структуру проекта» | «Новые обработчики API — в src/api/handlers, по одному на файл» |
| «Не используй default export» | «Используй именованные экспорты, а не экспорт по умолчанию» |

- Конкретно и проверяемо; называйте, **что делать вместо**.
- Выделение «ВАЖНО» — бюджет на 2–3 действительно важных правила, не больше.
- Каждая ошибка Claude — отчёт об ошибке в CLAUDE.md: «добавь это в CLAUDE.md». И наоборот: **строку, которую не можете обосновать, удаляйте.**
- Совет курса: начните без CLAUDE.md, посмотрите, где приходится поправлять Claude, и только потом <code>/init</code>.

## Навык проверки {#verify-skill}

Первый навык, который стоит написать, — **проверка**. Он срабатывает после изменений: запустить тесты → прочитать diff → убедиться, что ни один тест не ослаблен → отчёт «прошло/не прошло» с доказательствами.

> «Готово» — это не «код выглядит правильно». Готово — это когда проверки запущены и результат назван явно.

```markdown
---
name: verify-changes
description: Проверяет изменения после правок кода — тесты, diff, ослабленные
  тесты — и даёт отчёт с доказательствами. Используй после любого рефакторинга
  и перед коммитом.
---
1. Запусти ./scripts/check.sh и покажи вывод целиком.
2. Прочитай git diff. Найди тесты, которые пропущены, удалены или ослаблены.
3. Найди новые зависимости и вписанные в код адреса и ключи.
4. Найди реальные данные клиентов в тестах и примерах.
5. Отчёт: прошло / не прошло, по каждому пункту — доказательство.
```

Положите навык в <code>.claude/skills</code> проекта — и он будет у всей команды. Что куда: **CLAUDE.md** — постоянные правила; **навык** — процедура под тип задачи; **хук** — то, что нельзя пропустить. Правило: дважды набрали одну и ту же многошаговую инструкцию — это навык. Подробно — [Навыки Claude: полное руководство](page:kb/guides/skills-complete-guide).

## Режимы разрешений {#modes}

| Режим | Что делает | Где уместен |
| --- | --- | --- |
| Manual | спрашивает перед правками и командами | чувствительный код, начало работы |
| Accept edits | правит файлы и простые файловые команды без вопроса | знакомая задача под присмотром |
| Plan | только изучает и предлагает план | разобраться до правок |
| Auto | отдельная модель проверяет каждое действие и блокирует опасное | работа без присмотра |
| Don't ask | выполняет только заранее разрешённое, остальное молча отклоняет | CI, задания по расписанию — ничего не «зависнет» на вопросе |
| Bypass | без каких-либо проверок | **только** в изолированном контейнере без сети |

- Shift+Tab переключает Manual, Accept edits, Plan и Auto.
- В новых версиях интерактивные сессии **начинаются в режиме Auto**.
- Важно: проверка в Auto оценивает **намерение, а не правильность**. Сломанная авторизация пройдёт проверку — «сломанное не значит опасное». Поэтому Auto сочетают с хуком, который гоняет тесты.

## Хуки: то, что должно произойти {#hooks}

Около тридцати событий; ключевые для долгой работы:

| Событие | Зачем |
| --- | --- |
| PreToolUse | главный инструмент принуждения: запретить, разрешить или изменить действие до выполнения |
| PostToolUse | форматирование и проверки после правки |
| Stop / SubagentStop | «ты ещё не закончил»: не дать завершиться, пока тесты не проходят |
| SessionStart с фильтром <code>compact</code> | вернуть ключевые правила после сжатия контекста |
| InstructionsLoaded | аудит того, что попало в контекст |

### Коды выхода {#exit-codes}

- <code>2</code> — заблокировать (сообщение уйдёт Claude). Stop с кодом 2 не даст сессии завершиться.
- <code>1</code> — **не блокирует**, только сообщает об ошибке.
- PostToolUse блокировать поздно: действие уже выполнено.

### Где хуки ненадёжны {#hook-gaps}

- PreToolUse, упавший по таймауту, **пропускает** действие.
- Stop-хук снимается после восьми блокировок подряд без действий — проверяйте поле <code>stop_hook_active</code>.
- Если организация разрешила только управляемые хуки, перестаёт работать <code>/goal</code>.

Полезный приём — **«замаскировать, а не запретить»**: PreToolUse находит в команде секретный ключ и подменяет его заглушкой, вместо того чтобы останавливать работу. Основы — в руководстве [Хуки в Claude Code](page:kb/guides/claude-code-hooks).

## Запуски по расписанию и без диалога {#automation}

Лестница выбора — от «ничего не строить» к собственной программе:

<ol class="rai-flow">
<li><b>Routines</b><span>запрос + репозиторий + подключения + запуск по расписанию, вызову или событию GitHub; работает в облаке Anthropic</span></li>
<li><b>claude -p</b><span>запуск из скрипта или CI без диалога</span></li>
<li><b>Agent SDK</b><span>собственная программа с Claude внутри</span></li>
</ol>

### Routines {#routines}

<code>/schedule ежедневная проверка зависимостей в 9:00</code> или через claude.ai/code/routines. Минимальный интервал — час; запуск из свежей копии основной ветки; отправка изменений — только в ветки <code>claude/*</code>. Все подключения по умолчанию **включены** — уберите лишние; сеть держите в режиме «Trusted»; защитите основную ветку так, чтобы подключённый аккаунт не мог обойти защиту. Владелец организации может выключить routines совсем.

### claude -p {#headless}

```bash
claude -p "кратко опиши изменения в этом diff"

# структурированный ответ по схеме
claude -p "перечисли функции модуля" --output-format json \
  --json-schema '{...}' | jq '.structured_output'

# без присмотра: только заранее разрешённое
claude -p "исправь ошибки линтера" --permission-mode dontAsk \
  --allowedTools "Edit,Bash(npm run lint *)"
```

**Важное расхождение с курсом.** Сам по себе <code>-p</code> **загружает тот же контекст, что и обычная сессия**, — включая хуки из <code>.claude/settings.json</code> и подключения из <code>.mcp.json</code> репозитория, причём **без диалога доверия**. Пропускает их только флаг <code>--bare</code>. Для CI на чужом или непроверенном коде используйте <code>--bare</code> и явно передавайте нужное флагами (<code>--settings</code>, <code>--mcp-config</code>). <code>--bare</code> даёт воспроизводимую настройку, а не одинаковый ответ модели, и требует ключа API. Если ключа API нет, есть флаг <code>--setting-sources user</code>: с ним Claude Code не читает ни настройки проекта, ни его <code>.mcp.json</code>.

Успех запуска — код выхода 0; для <code>--output-format stream-json</code> смотрите и список отклонённых действий.

## Запросы на слияние: Code Review и GitHub Actions {#github}

<div class="rai-cards rai-cards--2">
<article><h3>Code Review</h3><p>Управляемый сервис ревью PR: включает администратор; запуск при открытии PR, на каждый push или по <code>@claude review</code>. Анализирует изменения на фоне всей кодовой базы, оставляет комментарии с уровнем серьёзности. <b>Никогда не одобряет и не блокирует</b> PR. Исправлять — локально: <code>/code-review --fix</code>. <article><h3>GitHub Actions</h3><p><code>/install-github-app</code> (нужны права администратора репозитория), действие <code>anthropics/claude-code-action</code>. Запуск по упоминанию <code>@claude</code> или по своему запросу и расписанию. Для отчётов — только инструменты на чтение и без вопросов.</p></article>
</div>

Правила для Actions: секреты — только через GitHub Secrets или федерацию удостоверений; минимальные права workflow; предел ходов <code>--max-turns</code>, таймауты и ограничение параллельных запусков; слияние — только после ревью человеком.

## Проверка работы без присмотра {#trust}

<ol class="rai-principles">
<li><b>Глубина проверки — по степени автономии</b><span>Чем меньше вы видели, тем строже проверка.</span></li>
<li><b>Сначала diff, потом резюме</b><span>Резюме пишет тот, кто работал; diff не врёт. Сначала файлы из плана, потом всё, что вне плана.</span></li>
<li><b>/code-review и «холодный» помощник</b><span>Свежий взгляд без памяти о том, как писался код. Уровни: <code>/code-review low</code>, <code>/code-review high</code>.</span></li>
<li><b>Тесты как ворота</b><span>Stop-хук с тестами плюс PostToolUse с линтером и проверкой типов; код 2 возвращает ошибку Claude.</span></li>
<li><b>Не ослаблены ли тесты</b><span>Пропущенные, удалённые и «смягчённые» тесты — отдельная проверка.</span></li>
<li><b>Для запусков из скриптов</b><span>Смотрите JSON-результат и код выхода, а не только текст.</span></li>
</ol>

### Три кучки находок {#piles}

Находки ревью раскладывайте на три кучки: **исправить сейчас / спросить почему / оставить**. Ревьюер, которого попросили искать проблемы, найдёт их всегда; если гнаться за каждой, код обрастает лишними абстракциями. Принимайте то, что влияет на правильность и требования.

Хорошие запросы:

```
Проверь изменения, которые ты только что сделал. Сообщи о проблемах,
ничего пока не исправляй.

Ты написал, что isValidEmail не обрезает пробелы, но в строке 4
вызывается trim(). Проверь ещё раз: находка в силе?

Исправь первую находку. Затем запусти тесты и покажи вывод.
```

## Параллельная работа и плагины {#scale}

### Фоновые сессии (Agent view) {#agent-view}

<code>claude agents</code> — один экран со всеми фоновыми сессиями и их статусами (работает, ждёт ответа, завершена, ошибка). <code>claude --bg --name "flaky-test-fix" "…"</code> — запустить в фоне. Учтите: фоновая сессия сама работает в отдельной копии репозитория и **может сама делать коммит, отправку и черновой PR** (кроме отправки в main, принудительной отправки и слияния). Если git должен оставаться под ручным контролем — пропишите это в CLAUDE.md. Каждая фоновая сессия расходует лимит отдельно.

### Динамические сценарии (workflows) {#workflows}

Для задач на десятки и сотни шагов Claude пишет план-сценарий, который запускает множество помощников: «исправляй, пока <code>npx tsc --noEmit</code> не пройдёт или два круга не дадут прогресса», «проверь каждый изменённый файл и дай одну сводку». Встроенный <code>/deep-research вопрос</code> — исследование. Ход — в <code>/workflows</code>. Перед запуском показывается план; пределы — 16 агентов одновременно; для больших запусков — предупреждение о расходе. Организация может отключить сценарии.

### Помощники в параллель {#fan-out}

«Исследуй модули авторизации, базы данных и API параллельно, отдельными помощниками»; <code>/batch инструкция</code> делит изменение на 5–30 помощников, каждый в своей копии. Сначала — на 2–3 файлах, потом на всём. Подробно о помощниках — [Помощники в Claude Code](page:kb/guides/claude-code-subagents).

### Плагины {#plugins}

Плагин объединяет навыки, помощников, хуки и подключения: <code>/plugin install github@claude-plugins-official</code>; командный каталог — <code>/plugin marketplace add организация/claude-plugins</code>. **Плагин выполняет код с вашими правами**, а его хуки добавляются к вашим. Версионируйте плагины как зависимости.

## Безопасность в регулируемой организации {#safety}

<ol class="rai-principles">
<li><b>-p без --bare выполняет настройки из репозитория</b><span>Хуки и подключения запускаются без диалога доверия. Для CI — <code>--bare</code> и явные настройки.</span></li>
<li><b>Зафиксируйте режим по умолчанию</b><span>Новые версии начинают в Auto. Задайте режим в настройках организации и запретите Bypass; Bypass — только в изолированном контейнере без сети, под непривилегированным пользователем.</span></li>
<li><b>Auto проверяет намерение, не правильность</b><span>Задайте доверенную инфраструктуру и внутренний реестр пакетов; правильность закрывайте тестами в Stop-хуке.</span></li>
<li><b>Знайте слабые места хуков</b><span>Код 1 не блокирует, таймаут пропускает действие, Stop снимается после восьми блокировок.</span></li>
<li><b>Routines работают в облаке Anthropic</b><span>Решите, допустимо ли это для ваших репозиториев; лишние подключения — выключить; основная ветка — защищена.</span></li>
<li><b>Фоновые сессии сами работают с git</b><span>Если нужен ручной контроль — запретите в CLAUDE.md.</span></li>
<li><b>GitHub Actions — минимальные права</b><span>Секреты через Secrets, пределы ходов и времени, слияние только после человека.</span></li>
<li><b>Плагины — только из разрешённых каталогов</b><span>Список разрешённых каталогов и ограничение хуков — через настройки организации.</span></li>
<li><b>Откат — это git</b><span>Возврат в Claude Code не отменяет команд оболочки и правок фоновых помощников.</span></li>
<li><b>Считайте расход</b><span>Фоновые сессии и сценарии расходуют лимит кратно; для организации есть ограничения сценариев.</span></li>
</ol>
