## Технический проект {#technical-design-page}

На странице описано, что создаётся в рамках пилота, чтобы IT-функция могла оценить объём работ, а представители контрольных функций — протестировать решение. Страница поясняет раздел 3 описания решения («Архитектура и данные»); полный проект хранится в архитектурном репозитории Центра Компетенций, а выбор продуктов и фреймворков фиксируется в журнале решений. Системы, показатели и данные Банка на странице не называются. Требования пилота к IT приведены на странице [«Контрольный лист готовности IT»](#it-readiness), различия между клиентскими маршрутами — на странице [«Технические профили клиентских маршрутов»](#journey-profiles). Проект не привязан к конкретному клиентскому маршруту: с технической точки зрения рекомендуется маршрут «Решение вопросов по платежам», но окончательно клиентский маршрут выбирается при одобрении бизнес-кейса.

### Сводка для одобряющих лиц {#technical-design-summary}

| Вопрос | Позиция |
| --- | --- |
| Что создаётся | Один ассистент для одного клиентского маршрута и одной группы обслуживания клиентов. Сервис клиентского контекста объединяет контакты, обращения и статус клиента; в рамках фиксированного workflow эти сведения передаются модели AI, которая готовит сводку и предлагает следующий шаг; панель рабочего места показывает результат работнику, который принимает решение и выполняет действие. |
| Что разрешено ассистенту | Читать контекст, который ему передаётся в рамках workflow, и возвращать структурированный результат: хронологию, вероятное препятствие с пометкой «вывод модели», процедуру со ссылкой на источник, следующий шаг из утверждённого перечня действий и черновик текста. |
| Что запрещено ассистенту | Иметь инструменты и что-либо записывать; устанавливать личность клиента, статус, соответствие условиям или сроки; перемещать денежные средства, изменять состояние обращения, принимать регулируемые решения и отправлять что-либо клиенту. Любая запись — это действие работника на рабочем месте. |
| Ожидаемая категория риска | 2: персональные данные клиентов; результат используется работником при принятии решения и доходит до клиента только после проверки работником. Если бы модель получила инструменты записи, решению была бы присвоена категория риска 3. |
| Место работы модели | В Банке. Внешняя модель — только после проверки поставщика и одобрения применения для класса данных; подключение внешней модели в дальнейшем является существенным изменением (см. [Развёртывание и маршрут к модели](#technical-design-model-route)). |
| Фазы | 1 — эксперимент в лабораторной среде на выгрузках с доступом только для чтения, который завершается отчётом о результатах. 2 — первое решение: сервис, который эксплуатирует Центр Компетенций, с правилом вывода из эксплуатации; развёртывается для первых пользователей (одной группы обслуживания клиентов) после валидации, окончательной приёмки командой и одобрения в порядке управления изменениями Банка. |
| Разработка, тестирование, одобрение | Решение создаёт руководитель Центра Компетенций в качестве инженера решений; тестирование и проверку выполняет лицо, не участвовавшее в разработке (п. 4.4 Операционной модели); описание решения и применение для класса данных одобряет куратор Центра Компетенций. |
| Требования к IT | Доступ на чтение к источникам клиентского маршрута, маршрут к модели внутри Банка, среды, регистрация событий, поддержка и управление изменениями: см. [«Контрольный лист готовности IT»](#it-readiness). |
| Трудозатраты, тайм-бокс, затраты | [оценка руководителя Центра Компетенций: трудозатраты по ролям, число итераций на каждую фазу]; [оценка руководителя Центра Компетенций: эксплуатационные затраты и затраты на модель в расчёте на одно обращение, с указанием источника]. Лимиты затрат на одно обращение включаются в условия применения. |

### Где генеративный AI создаёт ценность {#technical-design-genai-value}

Генеративный AI применяется там, где работу трудно описать устойчивыми правилами: для интерпретации разрозненных заметок по контактам, чатов, обращений и жалоб на русском или кыргызском языке либо со смешанным текстом; восстановления краткой хронологии; отделения текущей потребности клиента от прежних запросов; объяснения вероятного препятствия; применения соответствующей утверждённой процедуры; предложения допустимого следующего шага; подготовки черновика объяснения с опорой на источники для проверки работником.

Генеративный AI не устанавливает личность клиента, статус платежа, соответствие условиям, сроки, права и результат операции. Это факты и решения, которые предоставляют достоверные банковские системы и утверждённые правила. Это положение включается в условия применения в описании решения.

### Архитектура {#technical-design-architecture}

| Компонент | Назначение |
| --- | --- |
| Банковские системы | Хранят факты и обеспечивают процессы Банка. Пилот читает из них данные и ничего в них не изменяет. |
| Сервис клиентского контекста | Формирует для клиентского маршрута минимальное разрешённое представление данных: связанные записи, хронологию, ссылку на источник для каждого значения. Это не единое представление клиента «на 360 градусов». |
| Ассистент: фиксированный workflow, модель AI за шлюзом AI, поиск и извлечение знаний | В рамках workflow вызываются сервисы чтения и поиск, контекст передаётся модели, а её структурированный результат проходит контроль. Модель ничего не вызывает и ничего не записывает. |
| Рабочее место | Показывает результат рядом с рабочим столом системы обслуживания. Работник принимает, исправляет или отклоняет результат, проводит разбор или эскалирует обращение и выполняет действие. Само рабочее место ничего не отправляет. |
| Фиксация решений и результатов | Сохраняет вклад AI, решение работника и результат в собственном хранилище данных пилота. Обратная запись в системы Банка не выполняется. |

Порядок обработки обращения: работник открывает обращение, отвечающее критериям отбора; в рамках workflow проверяются полномочия работника, цель и соответствие обращения критериям, читаются источники и извлекается процедура; модель возвращает структурированный результат через шлюз AI; затем в рамках workflow контролируются схема, ссылки на источники и соответствие кода действия утверждённому перечню. Если результат не прошёл контроль, обязательный источник отсутствует или два источника противоречат друг другу, предложение не отображается и обращение передаётся на ручную обработку. Затем работник выполняет действие, а в записи сохраняется, что предложил AI и что решил работник.

### Пути получения информации {#technical-design-information-paths}

- **Исторические выгрузки в лабораторной среде (фаза 1).** В лабораторную среду загружаются выгрузки с доступом только для чтения; для каждой указаны владелец источника и класс данных. На их основе формируются исторические обращения для разработки, оценки и определения базовых значений. Персональные данные предварительно минимизируются и оцениваются совместно с представителем контрольной функции по защите данных. Обратная запись не выполняется.
- **Чтение рабочих данных (фаза 2).** После валидации при открытии обращения, отвечающего критериям отбора, интерфейсы чтения или адаптеры получают текущее состояние. Для каждого значения указываются источник и актуальность. Отсутствующие, устаревшие, противоречивые или ошибочно связанные сведения отмечаются как нештатная ситуация, и обращение обрабатывается в действующем ручном порядке.

Источниками являются единая база клиентских данных или CRM-система, система клиентского маршрута, система обращений, платформы контактов, система учёта жалоб, хранилища знаний, сервисы идентификации и управленческая отчётность; каждый источник сохраняет статус достоверного источника, а читаются только поля, необходимые для клиентского маршрута. Правила интеграции: версионируемые контракты, чтобы модель, workflow, рабочее место и адаптеры можно было заменять независимо друг от друга; логика клиентского маршрута находится в решении; снимки используются для оценки и никогда — как рабочий источник достоверных данных; у модели нет доступа к основным базам данных, учётным данным, шинам сообщений и неограниченному поиску; ссылки на источники сохраняются на всём пути от контекста до результата.

**Допущения, которые подтверждаются в ходе проработки, и резервный вариант для каждого из них:**

- нет интерфейса чтения — плановая выгрузка для лабораторной среды и более узкий объём работы с рабочими данными;
- нет общего ключа клиента — утверждённое правило сопоставления; неоднозначные совпадения помещаются на карантин;
- в системе обращений нет отметок времени по шагам — трудозатраты на обработку определяются по другому указанному источнику либо этот показатель исключается;
- записи на русском или кыргызском языке, со смешанным текстом или в транслитерации — оценочный набор охватывает каждый используемый язык;
- голосовые звонки — не входят в пилот, транскрибирование не проводится;
- нет прямых ссылок на записи — вместо них отображается идентификатор записи.

### Сервис клиентского контекста {#technical-design-context-service}

Сервис, настроенный на конкретный клиентский маршрут. Он связывает клиента, событие клиентского маршрута, открытое обращение и связанные с ним контакты по идентификаторам Банка; приводит их к единой хронологии событий обслуживания; хранит факты, расчётные значения и выводы модели раздельно; применяет ограничения по цели, роли, полям и срокам хранения; указывает для каждого значения источник, время, актуальность и владельца; формирует воспроизводимый снимок для каждого обращения к модели и каждого действия работника. Каждое событие содержит идентификаторы, исходную запись, тип и время в бизнес-процессе, статус или код причины, ответственную очередь, класс доступа и признак актуальности. Выводы модели хранятся отдельно — с обоснованием, версиями модели и запроса к модели и сроком действия — и никогда не становятся фактами о клиенте. Результаты пилота используются только для решения вопросов клиентов и оценки ассистента.

### Ассистент и действия работника {#technical-design-assistant}

Ассистент является ассистентом в значении корпуса документов: он готовит материалы для работника и не выполняет действий за пределами своего результата. Это один фиксированный workflow, а не открытый цикл. В рамках workflow обеспечиваются фиксированная последовательность и ограничение числа шагов; схемы запросов и ответов; ограничения времени, числа вызовов и затрат на одно обращение; контроль ссылок на источники; разделение фактов и выводов модели; остановка по правилу при отсутствии источников или противоречии между ними; переход к ручной обработке при любом сбое; решение работника до любого сообщения клиенту или действия. Средство исполнения workflow выбирает команда, и это управленческое решение вносится в журнал решений; версии модели, запроса к модели и настроек поиска прикладываются к трассировке каждого обращения. Протоколы взаимодействия AI-агентов не применяются: workflow один, AI-агента нет.

#### Функции и их пользователи {#technical-design-functions}

| Функция | Пользователь | Последствия |
| --- | --- | --- |
| `get_customer_service_context`, `get_journey_status`, `get_related_contacts`, `get_open_case`, `get_applicable_procedure`, `get_permitted_actions` | workflow | только чтение в пределах профиля клиентского маршрута |
| Хронология, вероятное препятствие, следующий шаг (код действия), черновик объяснения, черновик заметки по обращению, предварительно заполненное направление к специалисту | модель — в составе результата | за пределами рабочего места отсутствуют |
| Фиксация решения и обратной связи; фиксация результата обслуживания | работник — нажатием кнопки | запись в хранилище данных пилота |
| Создание направления к специалисту; сохранение заметки по обращению | работник — после проверки черновика | запись через действующий интерфейс, а при его отсутствии — вручную |
| Объяснение клиенту | работник — своими словами или отправкой отредактированного черновика через действующий канал | решение ничего не отправляет |

Ни одна функция не перемещает денежные средства и не отменяет операции с ними, не изменяет достоверное состояние по клиентскому маршруту, не принимает регулируемых решений, не определяет возмещение, не изменяет статус в части мошенничества, противодействия отмыванию денег и финансированию терроризма или санкций и не отправляет клиенту непроверенных сообщений. Профиль клиентского маршрута вправе только исключать пункты из этого перечня.

**Рабочее место.** Боковая панель на рабочем столе системы обслуживания или отдельный экран, если рабочий стол нельзя доработать. На рабочем месте отображаются запрос клиента; что произошло, с подтверждением из источников; подтверждённое текущее состояние; вероятное препятствие с пометкой «вывод модели»; применимая процедура; допустимый следующий шаг; предлагаемое объяснение с отметкой «Подготовлено AI»; идентификаторы записей; решение работника. Свободного чата на рабочем месте нет.

### Развёртывание и маршрут к модели {#technical-design-model-route}

| Вариант | Применение | Условия до передачи данных Банка |
| --- | --- | --- |
| Модель в Банке на действующей внутренней инфраструктуре запуска моделей | лабораторная и промышленная среды (по умолчанию) | проверка поставщика для модели, размещённой в Банке, или открытой модели (п. 4.4 Политики применения AI); лицензия зафиксирована (ARC-006); одобрение применения для класса данных |
| Новая инфраструктура запуска моделей в Банке | лабораторная и промышленная среды, если внутренней инфраструктуры нет | то же; мощности рассчитываются по замерам в лабораторной среде ([наблюдения за нагрузкой](#it-readiness-capacity)) |
| Внешняя управляемая модель | только промышленная среда, в лабораторной среде — никогда | проверка поставщика представителями контрольных функций по информационной безопасности, защите данных и правовым вопросам (пп. 4.1, 4.3 Политики применения AI); одобрение применения для класса данных; подтверждение EXT-001 и EXT-002 представителями контрольных функций |

Шлюз AI позволяет Банку впоследствии сменить модель; любая смена модели, версии или маршрута является существенным изменением. Рабочее место, workflow и сервис контекста работают на обычных серверах приложений; графические процессоры нужны только для запуска моделей.

Эксплуатация сервиса в фазе 2:

- три среды: лабораторная, тестовая (непромышленная) и промышленная; инфраструктура как код, управляемые секреты, отдельный технический идентификатор рабочей нагрузки;
- одна трассировка на обращение — от запроса до результата; сигнальные значения по качеству работы, дрейфу, частоте отмены и исправления результатов работниками, инцидентам и затратам, для каждого назначен ответственный за отслеживание (ARC-008);
- переход к представлению «только контекст» или к ручной обработке допускается всегда; второй маршрут к модели — только если он заранее прошёл валидацию и указан в описании решения; автоматическое переключение не применяется;
- первые пользователи поименно указываются в описании решения; расширение их круга — управленческое решение владельца направления и никогда не происходит автоматически;
- откат — в порядке управления изменениями Банка; инцидент AI обрабатывается в рамках процесса управления инцидентами Банка с уведомлением руководителя Центра Компетенций; протестированный механизм приостановления сохраняет записи об использовании (PLT-005, ARC-002).

### Подход к разработке и тестированию {#technical-design-engineering}

Код, инфраструктура, запросы к модели, схемы, настройки поиска, версии базы знаний и данные для оценки находятся под управлением версиями. Тесты создаются вместе с каждым компонентом; их выполняет лицо, не участвовавшее в разработке, а ссылка на результат приводится в каждой Feature (п. 7.1 Модели жизненного цикла решений).

| Уровень тестирования | Что подтверждается |
| --- | --- |
| Модульное, интерфейсное и контрактное тестирование | правила, схемы, маскирование данных и шаги workflow работают; контракты остаются совместимыми и обеспечивают контроль прав доступа |
| Качество данных | идентификаторы, сопоставление статусов, контроль актуальности, исключение полей и карантин работают |
| Поиск и извлечение информации | возвращается действующий источник; устаревшие, ограниченные в доступе и нерелевантные источники обрабатываются правильно |
| Оценка модели | подтверждённость фактов, интерпретация, следующий шаг, отказ от ответа и качество черновиков соответствуют критериям приёмки на каждом языке записей |
| Маршрут workflow | соблюдаются допустимые маршруты и ограничения; у модели нет ни одной функции |
| Предвзятость и ошибки | нет существенных различий в обработке значимых групп клиентов — до первого развёртывания для реальных пользователей или на реальных данных и в ходе мониторинга |
| Защищённость | обеспечена защита от промпт-инъекций через сообщения клиентов, несанкционированной выгрузки данных, доступа к данным другого клиента и уязвимостей компонентов с открытым исходным кодом |
| Отказоустойчивость | отработаны отказ источника, режим ограниченной функциональности, восстановление, задержки и приостановление |
| Экспертная оценка | эксперты направления подтверждают типовые состояния и нестандартные ситуации; результат служит подтверждающим материалом для оценочного набора |

Если обязательный тест не пройден, Feature остаётся на стадии «Проверка». Развёртывание выполняется в порядке управления изменениями Банка с заявкой на изменение и результатами тестирования; автоматический перенос между средами не применяется. После изменения модели, запроса к модели, корпуса знаний, сопоставления или workflow выполняется соответствующий регрессионный набор тестов, и руководитель Центра Компетенций решает, является ли изменение существенным и требует ли оно новой валидации.

### Данные и наборы для оценки {#technical-design-evaluation}

Используются три отдельных набора, за которые отвечают лица, не участвовавшие в разработке решения: обращения для разработки; зафиксированный набор обращений для приёмки, который не используется при разработке и образует оценочный набор, согласованный с направлением и размеченный экспертами направления; выборки рабочих обращений для мониторинга — в пределах цели, одобренной для класса данных. Исторические обращения псевдонимизируются так, чтобы связи между клиентом, событием, контактом и обращением оставались реалистичными; даты сдвигаются, только если при этом сохраняется порядок шагов процесса. Свободный текст на русском или кыргызском языке трудно полностью псевдонимизировать; если это невозможно сделать надёжно, данные, позволяющие установить личность, остаются в лабораторной среде на основании заключения контрольной функции по защите данных, а таблица повторной идентификации хранится вне лабораторной среды. По каждому обращению фиксируются исходное состояние, ожидаемая интерпретация, допустимое действие, процедура, исключённые случаи и обоснование эксперта.

| Режим | Что получает работник | Вопрос | Где сравнивается |
| --- | --- | --- | --- |
| Действующий процесс | действующие системы и процедуры | каковы базовые значения? | в промышленной среде, в сопоставлении с первыми пользователями |
| Представление «только контекст» | связанные факты, хронология, построенная по правилам, идентификаторы записей | что даёт объединение данных? | на зафиксированном наборе обращений; также служит режимом ограниченной функциональности |
| Представление с генеративным AI | контекст, а также сводка, препятствие, процедура, следующий шаг и черновик | что добавляет генеративный AI? | на зафиксированном наборе обращений и в промышленной среде с первыми пользователями |

Если основную часть улучшения даёт представление «только контекст», результат говорит в пользу инвестиций в клиентский контекст и ограничения дальнейших инвестиций в генеративный AI. Дополнительная ценность генеративного AI учитывается при управленческом решении по итогам MVP, но не является критерием по принципу «выполнено — не выполнено». Необходимое число обращений указано в приложении об измерениях на странице [«Паспорт инициативы»](#charter); правило приёмки — на странице [«Меры контроля и подтверждающие материалы»](#controls).

### Соответствие платформе AI и стандартам {#technical-design-platform-standards}

Пилот использует платформу AI там, где она уже есть. Временная замена функции платформы в рамках пилота фиксируется в разделе 3 описания решения, а также как зависимость от владельца платформы, который принимает такую замену для этого решения. Подтверждающие материалы приведены на странице [«Меры контроля и подтверждающие материалы»](#controls).

| Функция платформы AI или стандарт | Реализация в проекте |
| --- | --- |
| Шлюз доступа к моделям (PLT-004) | шлюз AI либо, в качестве временной замены, один прокси-сервер с аутентификацией; данные разделены по классам |
| Слой работы со знаниями (ARC-001) | один утверждённый корпус знаний; результаты содержат ссылки на источники; для каждого источника в реестре AI-решений указаны владелец и дата пересмотра |
| Шлюз доступа к инструментам (ARC-007) | не требуется: у модели нет инструментов, и она не является AI-агентом |
| Защитные механизмы платформы (ARC-005) | сообщения клиентов рассматриваются как недоверенные входные данные и фильтруются; результаты проходят контроль; перед каждым действием — решение работника |
| Контроль со стороны человека (ARC-004) | по каждому обращению решает работник; в записи сохраняются вклад AI и решение работника |
| Наблюдаемость (PLT-002, ARC-008) | регистрация событий с требуемым сроком хранения; трассировка каждого обращения; сигнальные значения с ответственными за отслеживание |
| Реестр AI-решений (PLT-001) | модель и версия, классы данных, источники знаний; «AI-агенты и права: нет» |
| Приостановление (PLT-005, ARC-002) | отключение генерации или всего сервиса без потери записей |
| Компоненты с открытым исходным кодом (ARC-006) | лицензии указаны в описании решения; компоненты охвачены тестированием защищённости |
| Лабораторная среда (LAB-001–LAB-007) | изоляция, регистрация событий, выгрузки с доступом только для чтения и с указанием владельцев, оценка персональных данных, оценочный набор с контролем опоры на источники, дрейфа и предвзятости, отчёт о результатах по завершении |

### В дальнейшем, за рамками пилота {#technical-design-later}

- Общий шлюз доступа к инструментам, сервис политик, среда исполнения workflow или потоки событий — только если они понадобятся второму клиентскому маршруту, в форме предложения владельцу платформы.
- Повторное использование компонентов — через описание пакета; для совместного использования нужен второй потребитель (п. 8.12 Модели жизненного цикла решений).
- Использование за пределами круга первых пользователей — по управленческому решению по итогам MVP, затем выпуск с контрольным листом приёмки либо предложение и передача решения IT-функции в качестве получателя.
- Самообслуживание клиентов или действия от имени клиентов — каждое из этих направлений оформлялось бы отдельной инициативой или предложением со своей категорией риска; AI, действующий от имени клиентов, относился бы к категории риска 3.
